# ADR-0002. Структура решения: три проекта вместо четырёх

- **Статус:** **Superseded by ADR-0006**
- **Дата:** 2026-11-13
- **Связано с:** [ADR-0001](0001-dotnet-avalonia-stack.md), [ADR-0004](0004-state-persistence-and-timer.md),
  [ADR-0006](0006-domain-application-projects.md)

> **Внимание.** Это решение заменено [ADR-0006](0006-domain-application-projects.md):
> Domain и Application выделены в отдельные проекты, чтобы границы слоёв
> проверялись компилятором. Текст ниже сохранён как история рассуждений и не является
> действующим.

## Контекст

Требуется разделить код на Domain / Application / Infrastructure / Presentation.
Классический подход предполагает четыре проекта. Однако предметная область здесь мала:
доска 9×9, набор правил, режимы игры. Отдельный слой «Application» (use-cases, оркестрация,
порты) не даёт самостоятельной ценности, если прикладная логика невелика и полностью
детерминирована — а это как раз случай Sudoku.

Требования к архитектуре:
- вся игровая логика тестируема без запуска окна;
- `Core` не знает про UI и файловую систему;
- приложение не обращается в сеть.

## Решение

**Три проекта** (плюс три тестовых):

```
Sudoku.Core             ← Domain + Application (слиты)
Sudoku.Infrastructure   ← persistence, puzzle bank, ФС
Sudoku.App              ← Presentation (Avalonia) + DI-композиция
Sudoku.Core.Tests
Sudoku.Infrastructure.Tests
Sudoku.App.Tests
```

Правило зависимостей (строго, без исключений):

```
App ──► Core
App ──► Infrastructure ──► Core
```

`Sudoku.Core` не содержит ни одной ссылки на Avalonia, `System.IO`, `HttpClient` или иной
инфраструктуры. Всё внешнее общение идёт через интерфейсы, объявленные в `Core`
(`ITimeProvider`, `IRandomSource`, `IStateStore`, `IPuzzleBank`) и реализуемые в
`Infrastructure` (или в тестах — как заглушки).

Внутри `Sudoku.Core` разделение на папки `Domain/` и `Application/` — **организационное**,
а не проектное: оно не создаёт циклов зависимостей и не требует отдельной сборки.

## Последствия

**Положительные**
- Меньше проектов → быстрее сборка, проще навигация, меньше церемонии.
- Игровой движок (`Sudoku.Core`) собирается в «чистом» .NET и тестируется за секунды —
  без инициализации Avalonia и без окон.
- Правило «Core не знает про UI» сохраняется, потому что это правило проекта, а не папки.
- Миграция на 4 проекта (выделение Domain) остаётся возможной без изменения кода:
  достаточно перенести файлы и заменить ссылку на проект.

**Отрицательные**
- При росте прикладной логики (например, добавление сетевой синхронизации, аккаунтов,
  нескольких фронтендов) слитое `Core` придётся разделять — рефакторинг структуры проектов.
- Правило зависимостей нужно поддерживать вручную (ревью/тест на ссылочный граф),
  так как компилятор не проверит «Core не знает про System.IO» — только запрет на
  `System.IO` даст ошибку компиляции, а запрет на Avalonia тоже. Фактически запрет
  достигается тем, что `Core` просто не ссылается на `App`.

## Альтернативы

| Вариант | Оценка |
|---|---|
| **4 проекта** (Domain / Application / Infrastructure / Presentation) | Отклонён: для Sudoku избыточно. Оправдан при нескольких фронтендах, сложной оркестрации или внешнем API |
| **1 проект** (всё в `Sudoku/App`) | Отклонён: невозможно тестировать логику без Avalonia, риск «логика в UI» |
| **2 проекта** (Core+Infrastructure / App) | Отклонён: смешивает «чистую логику» с файловой системой; тесты Core всё равно создают временные файлы |
| **Core / Infrastructure / App / Tools (CLI)** | Отложено: CLI-инструмент (генератор банка головоломок) будет полезен на этапе 5/12, добавим при реальной потребности |
