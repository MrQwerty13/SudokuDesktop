# ADR-0008. Решатель судоку: битовые маски, распространение ограничений и MRV

- **Статус:** Принято
- **Дата:** 2026-11-13
- **Связано с:** [ADR-0003](0003-difficulty-rating.md), [ADR-0006](0006-domain-application-projects.md)

## Контекст

Для игры нужен решатель, который:

1. находит решение головоломки;
2. умеет определять количество решений и останавливаться после обнаружения второго —
   этого достаточно для проверки уникальности и не требует перечисления всех решений;
3. различает отсутствие решения, единственное решение и несколько решений;
4. не мутирует исходное состояние;
5. детерминирован;
6. корректно обрабатывает некорректный ввод;
7. достаточно быстр для обычной игры.

Дополнительное требование из следующих этапов: движок решателя будет переиспользован
генератором (проверка единственности) и подсказчиком (пошаговое применение техник),
поэтому он должен быть вынесен в отдельный, независимый от UI компонент.

Рассматривались два подхода:

- **DLX / Algorithm X** (точное покрытие, 729×324) — классическое решение, но сложнее
  в реализации и медленнее на практике, так как требует построения матрицы и обхода
  dancing links;
- **битовые маски + constraint propagation + перебор с выбором ячейки по MRV** — подход
  Питера Норвига (https://norvig.com/sudoku.html), решает задачу в пределах сотни строк.

## Решение

Реализован `MrvSudokuSolver` в слое `Sudoku.Application` (интерфейс `ISudokuSolver`),
входная модель — неизменяемый `Sudoku.Domain.Grid`.

**Алгоритм**

1. **Состояние.** Для каждой строки, столбца и блока хранится 9-битная маска занятых цифр.
   Кандидаты ячейки вычисляются за O(1): `ALL & ~(row | col | box)`.
2. **Распространение ограничений** (повторяется до стабилизации):
   - *naked single* — у ячейки единственный кандидат, значение ставится сразу;
   - *hidden single* — для цифры в строке/столбце/блоке осталась ровно одна возможная ячейка;
   - отсутствие кандидатов у ячейки или отсутствие места для цифры в единице — противоречие,
     ветвь отбрасывается.
3. **Перебор.** Если после распространения остались пустые ячейки, выбирается ячейка с
   минимальным числом кандидатов (MRV); при равенстве — с наименьшим индексом.
   Перебираются цифры по возрастанию.
4. **Откат.** Назначения ведутся в стек (trail), откат выполняется до отметки, поэтому
   состояние восстанавливается точно и без копирования досок.
5. **Остановка.** Поиск прекращается, как только найдено `solutionLimit` решений.
   `Solve` использует предел 2, `CountSolutions(grid, limit)` — произвольный предел.

**Результат.** `SolveResult` содержит `SolveOutcome` (`NoSolution` / `UniqueSolution` /
`MultipleSolutions`), список найденных решений и признаки наличия/единственности решения.

**Вход.** `Grid` неизменяем, поэтому решатель физически не может изменить исходное
состояние. Некорректный ввод обрабатывается на границе: `Grid.FromString` выбрасывает
`ArgumentException` (неверная длина или символ), `TryFromString` возвращает `false`,
`null` и неположительный предел дают `ArgumentNullException` / `ArgumentOutOfRangeException`,
а доска с противоречивыми заданными цифрами даёт результат `NoSolution`.

**Детерминизм.** Порядок ячеек и цифр не зависит от состояния коллекций, поэтому
одинаковый вход всегда даёт одинаковый вывод (в том числе порядок найденных решений).

## Последствия

**Положительные**
- Один движок покрывает три задачи: решение, проверку уникальности и (в будущем) подсказки.
- Нет внешних зависимостей: только BCL.
- Измеренная производительность: классическая головоломка — ~1 мс, разреженная (40–48 подсказок)
  — 0–3 мс, поиск двух решений для полностью пустой доски — ~1 мс. Запас многократно
  превышает требование NFR-05.
- Отсутствие DLX упрощает поддержку и снижает риск ошибок.

**Отрицательные**
- Реализованы только приёмы первого уровня (singles). Приёмы уровня пар/троек (X-Wing и далее)
  в решателе отсутствуют: сложные головоломки решаются перебором, а не «человеческими» приёмами.
  Для рейтинга сложности по потолку техник (ADR-0003) потребуется отдельный логический решатель
  с лестницей техник — это задача этапа 4/5.
- Восстановление состояния через trail корректно, но требует аккуратности: любая новая
  операция изменения доски обязана сопровождаться корректным откатом.
- Алгоритм перечисляет решения путём перебора; для головоломок с очень большим числом
  решений (например, пустая доска) поиск первых двух решений быстр, но поиск «всех»
  решений непригоден — поэтому предел поиска обязателен в API.

## Альтернативы

| Вариант | Оценка |
|---|---|
| **DLX / Algorithm X** | Отклонён: сложнее в реализации и поддержке, для проверки уникальности избыточен |
| **Решатель на сканировании по порядку без MRV** | Отклонён: существенно медленнее (на порядки) |
| **Оценка сложности по времени решения** | Отклонён (см. ADR-0003): время зависит от порядка перебора и не отражает сложность для человека |
| **Модуль на C++/Python (sudoku-solver, Z3)** | Отклонён: внешняя зависимость и потеря детерминизма/простоты сборки |
| **Реализация в слое `Sudoku.Domain` | Отклонён: решатель — это сценарий (use case), а не доменный тип; домен остаётся чистым |
